# Agent Note: 一次性调试模式

Status: implemented

[English](2026-09-10-one-shot-debug-mode.md) | 中文

**关于调试模式的形态，已被[已记录调试模式](2026-09-16-logged-debug-mode.zh.md)取代：** 调试模式现在是与 plan mode 相同的逐 agent（智能体）已记录状态——`debug/mode` 事件、一个投影单元、携带工作流提示词（而非用户消息）的 `debug:policy` 系统提示词段落（order 550），以及一个输入框徽标。下文所列、已记录设计未反转的决策——判定作为工具结果交付、审阅失败边界、以及固定的 `{ prompt }` 配置——仍以本说明为家。日志捕获机制现为回环 debug-log 端点及其逐周期生命周期，由已记录调试模式说明描述。

## Problem

调试一个报告的 issue（问题）是一个多步交换——调查、加日志、让用户运行、读日志、修复、重复——而现有的逐轮对话只有在用户手动驱动每次交接时才能处理它。没有一个一等公民的「停下来收集证据」边界：模型无法像 plan mode 在审阅式退出上阻塞那样，干净地阻塞在一个人类判定上（「复现了吗？」「修好了吗？」），也没有任何东西拥有临时日志文件的生命周期，因此插桩与陈旧的 `debug.txt` 内容会在多次尝试间累积。

plan mode 的自然镜像是错误形状。plan mode 是记录到日志的逐 agent 状态（`plan/mode`），能跨恢复与 fork 存活，且需要一个边界追加；而一次调试会话是模型驱动的一次性、可重复循环，没有要恢复的持久立场。照抄 plan mode 的状态机会为一个不存在的状态添加一个已记录事件、一个投影单元和一个恢复/fork 折叠。

## Decision

调试模式是无状态的一次性工作流，由 `@deepseek-ai/dsh-debug` 拥有，位于 `packages/debug/debug-mode/`（`ctx.debug`，`DebugModeController`）。它不注册提示词段落，不保留已记录模式，不贡献会话事件；循环由模型驱动，审阅之间会话就是普通对话。

两个面向模型的入口驱动它。当 `ctx.commands` 被组合时，`/debug <issue>` 要求携带一个 issue，并把部署方 `prompt` 加报告的 issue（连同任何被接纳的附件）通过 `agent.steer()` steer 为一条普通已记录用户消息。`finish_debug` 接收以有序列表形式提供的复现该 issue 的步骤（仅此而已），并在[用户交互 seam](../../../../docs/subsystems/user-questions.zh.md) 上阻塞，等待 **Proceed**（继续）或 **Mark as fixed**（标记已修复）判定；判定作为工具结果交付给模型，而不是单独 steer 的消息，因此无需新事件就保持「模型可见 ⟺ 已记录」规则成立。

一次性调试的日志捕获机制——工作区根目录下由模型写入的 `debug.txt`，宿主在 **Mark as fixed** 时把它截断为 0 字节，**Proceed** 时缺失则产生一条未找到说明（判定仍为 `reproduced`）——已被回环 debug-log 端点取代，该端点由[已记录调试模式](2026-09-16-logged-debug-mode.zh.md)说明拥有：插桩在模式激活期间向逐会话端点 POST 条目，**Proceed** 把当前周期捕获的条目作为工具结果返回。

配置恰好是 `{ prompt: string }`；`prompt` 缺失、为空白或不是字符串，以及任何未知键，都会在加载时失败。presets 以一个参考工作流提示词挂载该包。

### 边界与模型契约

被拒绝的审阅（用户夺回轮次去输入而不是选择）是一次失败的调用，告诉模型保留插桩并等待；缺失的交互通道和审阅期间的服务重载同样失败，而不是静默继续。只有 Web UI 有 `debug-review` 呈现；其他交互提供方通过其通用选项流程呈现同一请求。

## Alternatives considered

**已记录的调试模式状态（plan mode 镜像）。** 这买来恢复/fork 存活，但该循环没有要恢复的持久立场，边界追加机制会空转；无状态循环更便宜，且贴合产品。

**用户 steer 的「复现/修好」消息，而不是工具结果。** 这让 `finish_debug` 成为一个即发即忘探测，但判定就不会成为模型下一步的已记录载体，且模型需要解析一条自由形式消息；轮内工具结果是自然载体。

**可配置或模型选择的日志路径。** 这为没有产品需求而增加一个要校验和沙箱化的模型供给输入；固定的工作区根常量让宿主与模型就一个位置达成一致。

**宿主在 Mark as fixed 时删除 `debug.txt`。** 删除后没有文件供模型确认为干净，且让一次重跑从缺失路径开始；截断为 0 字节（缺失时创建）给出一个稳定、可检查的后置条件。

## Consequences

这一权衡买来一个干净、可重复的调查与收集循环，带有人类判定点和宿主拥有的日志生命周期，代价是单一、有上限的宿主拥有日志捕获通道（没有多文件或可配置日志），以及只有 Web UI 才渲染为判定卡片的审阅。因为没有已记录状态，审阅期间进程退出会丢失进行中的审阅（模型必须重新呈交）——与在某轮最后一个 pre-step 之后作出的 plan mode 选择同类——且因为 `finish_debug` 是一个稳定的、始终存在的工具 schema，它在会话之外不增加任何 token。
